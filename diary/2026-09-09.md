# 2026-09-09 — The Runs API

## 22:22 — Runs backend built against a live Dagster

Jira: GP-12 (epic Runs) · GP-13..GP-16 built · GP-17, GP-18 open

### What changed

**A new `backend/apps/runs/`**, no models and no migration — every request
proxies Dagster live. `dagster.py` is the only module that speaks GraphQL,
in the shape `apps/map/catalog.py` set. Four endpoints: `GET /api/runs/`,
`GET /api/runs/{id}`, `GET /api/runs/{id}/logs`, `POST /api/runs/trigger`.
`httpx` pinned and added; five `DAGSTER_*` settings, all defaulted.

**`context/integrations/dagster.md` is new** and holds the confirmed
schema. Everything in it was read off a live Dagster 1.13.19, started from
`../gobase` with `dagster dev -m gobase_orchestration.definitions`.

30 new tests, 50 backend tests green, contract regenerated, frontend
builds. Four commits on the `Runs` branch, not pushed.

### Decisions

- **The trigger is `POST /api/runs/trigger`, not `/launch/`.** GP-16 said
  launch; docs/adr/004 says trigger and `IsAdmin`'s docstring already
  named that path. The ADR won and GP-16 needs correcting in Jira. No
  trailing slash on the leaves, matching every other endpoint — ADR-004's
  trailing slash is prose, not the decision it records.

- **Per-step detail comes from `Run.stepStats`, not from the event log.**
  It gives step key, status and timing directly. So `specs/runs.md` (per-
  step detail) and GP-15 (event log) are both served without either
  faking the other.

- **The page will poll while a run is going.** This reverses
  `specs/runs.md`, `context/architecture.md` and `context/ui-rules.md`,
  which all said manual refresh only. Recorded, not built; it needs an ADR
  when GP-17/GP-18 are built.

- **The launch guard treats `MANAGED` as in progress**, unlike GP-16's
  list of four statuses. Refusing a legitimate run is cheaper than
  starting a second copy of a 1TB sync.

### Problems solved

- **A rejected query looked like an outage.** Dagster answers a bad enum
  value with **HTTP 500 carrying a normal GraphQL `errors` body**.
  `raise_for_status()` ran before the body was read, so a client-side
  mistake became 503 "Dagster is unreachable". Fix: read the body first;
  a non-200 only means unavailable when there is no GraphQL error in it.

- **Every launch would have failed with a parse error.** Three of
  `launchRun`'s twelve union branches — `RunConfigValidationInvalid`,
  `InvalidStepError`, `InvalidOutputError` — have **no `message` field**.
  Asking for one does not fail that branch, it invalidates the whole
  document. Found by actually launching. They are now named by
  `__typename` only. All four query documents are validated against the
  live schema.

- **Event timestamps are a different type from every other time.**
  `Run.creationTime`/`startTime`/`endTime` and `RunStepStats` times are
  `Float` seconds; an event's `timestamp` is a **`String` of
  milliseconds**. Both become ISO 8601 UTC before leaving the backend.

- Smaller ones: the logs cursor argument is `afterCursor`, not `cursor`;
  `RunsFilter` has no `jobName`, only `pipelineName`; `RunStatus` has
  **nine** values (`MANAGED` is the easily-missed one); `PythonError.stack`
  is a list.

### Open threads

- **`failure_summary` is verified against fixtures only.** The one real
  run made was a success. Making a failed run would need an asset that
  fails, which was outside what was authorized.
- **`_first_failure` reads forward.** The log cannot be filtered or read
  backwards, so a failed run's error is found by paging from the start,
  capped at 5 pages of 1000. A run that fails very late reports no
  summary. Untested against a real late failure.
- **The in-flight guard races.** A run can start between the check and the
  launch. It catches the double-click, not a genuine race.
- **GP-16 still says `/launch/` in Jira** and needs editing.
- **Nothing verifies the queries against a live schema in CI**, so a
  Dagster upgrade that renames a field breaks at runtime, not in CI.
