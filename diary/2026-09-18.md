# 2026-09-18

## 13:00 — Address search, the first outside service, and a data defect that fixed itself

Jira: GP-1 (epic Map). Local only; nothing deployed this session.

### What changed

**Assets pages instead of Load more.** `useAssetPages` (infinite query) became
`useAssetPage` (one page, `keepPreviousData`), and a new hand-rolled
`ui/Pagination` sits under the grid. **12 per page.** The readout changed from
`24 of 212 assets` to `1–12 of 212 assets`. Any filter or sort change returns
to page one; stepping pages scrolls the column back to the top.

**Address search, on both pages.** New `backend/apps/places` serving
`GET /api/places/search?q=`, proxying Esri's `findAddressCandidates`. One call
per search, up to five candidates, each a name, a point and a bbox.

- **Atlas:** `CoordinateSearch` became `PlaceSearch` — one box for both. Two
  numbers are a coordinate and never reach the geocoder; anything else offers
  candidates. Picking one mirrors `goTo` exactly (point mode, selection
  cleared, marker, assets-at-point) and frames the candidate's extent.
- **Assets:** the rail's search box now filters names *and* offers places,
  with a removable area chip under it. The two filters combine.
- New `bbox` parameter on `GET /api/catalog/assets`, filtering by
  `ST_Intersects` **inside the browse CTE**, so the page, the total and the
  per-type counts are all narrowed together.

**New frontend primitives:** `ui/useCombobox` + `ui/combobox` (ARIA 1.2,
hand-rolled, no new dependency), and `features/places/` — `useDebounced`,
`bbox`, `usePlaceSearch`, `PlaceOptions`, `useAreaParam`.

Docs: ADR-011, `context/integrations/esri.md`, plus updates to `specs/map.md`,
`specs/assets.md`, `context/ui-registry.md`, `context/architecture.md`,
`context/integrations/kb.md` and `CLAUDE.md`.

### Decisions

- **`apps/places`, not `apps/map` or `apps/catalog`.** ADR-010's "one URL, one
  question" test: the Assets page has no map on it and is the other caller, and
  `catalog/kb.py` is by its own docstring the kb reader — geocoding touches no
  table. ADR-011.
- **Nothing is cached, and that is the cheap answer.** Esri's *not stored*
  tier is free to 20,000/month then $0.50/1,000; *stored* has **no free
  allowance** at all, at $4.00/1,000. A cache is storage. So caching would add
  infrastructure in order to start paying. Client debounce instead.
- **The API key goes in a POST form body, never a query string.** In a request
  line it reaches proxy logs and comes back out inside `httpx`'s exception
  text. `EsriUnavailable` carries the exception *type*, not its message, for
  the same reason. There is a regression test for both.
- **A blank `ESRI_API_KEY` is a supported state.** 503 before opening a socket;
  the UI says address search is unavailable and latches, so a switched-off
  service is asked once a session rather than once a keystroke. The whole
  feature was built and tested without an ArcGIS account.
- **The data-type counts respect `bbox`.** ADR-010 excludes exactly one axis
  — the type filter — and its reason is self-referential. `q` and the date
  window already narrow the counts. An empty grid beside a rail reading
  `vector 34` reads as a broken page.
- **A URL parameter exists if, and only if, the state crosses a page
  boundary.** ADR-009 said the parameter set "deserves designing rather than
  growing"; this is the rule, and it explains the absences (`q`, sort, page,
  map mode, drawn layers) as much as the presences (`asset`, `place`, `bbox`).
- **`ST_Intersects`, not the `&&` box operator.** PostGIS puts a box index
  condition in front of it anyway, so the GiST index is used either way, and
  it stays correct if extents ever stop being rectangles.
- **The Assets search box does both jobs rather than choosing.** Chosen against
  advice — "Beirut" is genuinely ambiguous. Resolved by answering both ways and
  letting the user pick, which turned out better than either single answer.

### Problems solved

- **The knowledge base was refreshed and nobody noticed.** The 15 Sep entry
  records two hand-made assets with invalid zero-area extents, and planning
  this feature started from "area filtering will return nothing until the data
  platform fixes it". Read live: **76 active assets, 45 with extents, zero
  invalid, zero zero-area.** A Beirut box matches 21, a Dresden box 22, no
  overlap. The defect was fixed upstream. `context/integrations/kb.md` now
  records the new state and keeps the old reading as history.
  → **Read the database before planning around what the diary says about it.**
- **A new `unparsed` modality appeared** — 31 of the 76, no extent, no layer
  rows. It arrived with no code change, which is the rule about never holding a
  list of data types doing its job.
- **Refs read during render.** The 503 latch and the combobox highlight were
  both refs; the lint rule is right that a ref read during render cannot drive
  the render that needs it. Both are state set during render now.
- **`serializeBbox` normalises `34.0` to `34`.** Found by a failing test key.
  Harmless — one canonical form — but the URL you get back is not always the
  URL you pasted. Covered by a test that says so.
- **Two stale claims in `context/architecture.md`**, flagged on 8 Sep and still
  there: `GET /api/map/footprints?bbox=` never existed, and "retrieval via
  H3/bbox" is wrong because `kb` has no H3 extension. Both fixed here, because
  this is the change that introduces the first real bbox retrieval path.

## 16:45 — Getting the geocoder key in, and a key pasted into the wrong variable

Jira: GP-1 (epic Map). Local only; nothing deployed.

### What changed

- An ArcGIS Location Platform account exists and an API key was generated.
  `backend/.env` now carries all four `ESRI_*` settings. The value itself lives
  only there; `.env` is gitignored and was confirmed so.
- `context/integrations/esri.md` gained a short section on the two things that
  look like a broken key when a key is first added.

### Problems solved

- **`GET /api/places/search` returned 503 with a key in `.env`** → the key had
  been pasted after `ESRI_GEOCODE_URL=` instead of `ESRI_API_KEY=`, and the
  other three `ESRI_*` lines were never copied from `.env.example`. So the key
  was blank and the view short-circuited, which is the designed behaviour.
  → All four settings written properly. Confirmed live: `esri.find_places`
  returns five candidates for "Beirut", each with a bbox. The whole path from
  request shape to bbox parsing is real now, not just mocked.
  **The log line that identifies this case** is `Address search asked for, but
  no API key is configured`. It is what separates "no key" from "geocoder
  unreachable", since both answer 503.
- **A secret was read aloud.** The key was in a variable named `..._URL`, so it
  was printed while diagnosing. It never reached git, but it is in a terminal
  transcript. **Rotate it.** The lesson is narrower than "be careful": a
  variable's name is not evidence of what it holds, so check whether a value is
  *set* rather than printing it.

### Open threads

- **The frontend was still showing 503 when the session ended, and the cause
  was not confirmed.** Two candidates, both likely and both innocent:
  1. `manage.py runserver` started at 16:42:46, `.env` was fixed at 16:45:16.
     Django's reloader watches `.py` files, not `.env`, so the running process
     still holds the blank key. **Restart the backend first.**
  2. `usePlaceSearch` latches on a 503 for the life of the page, so a tab that
     already saw one will not ask again. **Reload the page after the restart.**
  Both are now written up in `context/integrations/esri.md`.
- **Rotate the API key** — see above. Delete the credential in the ArcGIS
  portal, generate a new one, paste after `ESRI_API_KEY=`, restart.
- Esri's terms and the OpenStreetMap basemap question are still unsettled
  (docs/adr/011, Open). Still blocks shipping, not building.
- Still not opened in a real browser with a working geocoder.
