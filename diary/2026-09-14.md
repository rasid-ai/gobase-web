# 2026-09-14 — Go to coordinates, and why no GeoJSON has ever rendered

## 21:45 — A small feature, and the bug it uncovered

Jira: GP-1 (epic Map). The coordinate feature has no ticket yet.

### What changed

**Go to a coordinate.** `frontend/src/features/workspace/coordinates.ts`
(parser) and `CoordinateSearch.tsx` (the box), wired into `MapWorkspace`
through a `goTo` that mirrors `onMapClick` and adds flying there and
switching the mode. Frontend only — the endpoint already existed.

**`optimizeDeps: { exclude: ['maplibre-gl'] }`** in `vite.config.ts`. This
is the important one; see below.

**The geometry filters now match Multi geometries**, and there is a
development-only `window.__map` handle.

26 new frontend tests, 71 total. Two commits: 7d851e6, 2cedcbe.

### Decisions

- **Latitude first in the input**, which is Google's order and the order a
  pasted pair arrives in. The API takes longitude first; the swap lives in
  the interface. One box, not two, so a pasted pair needs no editing.
- **Submitting switches the mode to point.** Otherwise the mode control
  would describe something other than what a click does.
- **A valid coordinate with no data still goes there**, silently — the
  same answer a click on empty space gets, so specs/map.md's "no panel, no
  error" rule did not need reversing. Only an unreadable coordinate errors.
- **A reversed pair is taken at face value** when both values are in
  range. It is undetectable; the label carries the order.

### Problems solved

- **No GeoJSON source had ever rendered in the dev server.** Not drawn
  vector layers, not asset footprints. Symptom: the request succeeds, the
  store fills, the map flies to the right place, the layers exist in
  `getStyle()` with valid paint and the source holds 163 valid features —
  and nothing paints, with no console error.

  Cause: MapLibre parses GeoJSON in a web worker and finds it with
  `new URL('./maplibre-gl-worker.mjs', import.meta.url)`, relative to where
  its own module was served from. Vite's pre-bundling moved the module to
  `.vite/deps` and left the worker behind, so the URL 404s and the worker
  never starts. The fetch is made by the worker loader, not the map, so
  nothing surfaces as a map error. The raster basemap kept working because
  raster tiles are decoded on the main thread — which is what made this
  look like a bug in whatever had been drawn most recently.

  Fix: exclude maplibre-gl from pre-bundling. **Development only** — the
  production build resolves the worker through Rollup and was never
  affected, so `pnpm build && pnpm preview` looks fine and hides this.

  Found only by inspecting the live map: `isSourceLoaded` false and
  `querySourceFeatures` 0 on a source with valid data.

- **`geometry-type` is not normalised.** `['==', ['geometry-type'],
  'Polygon']` drops every MultiPolygon. The catalog holds 12 MultiPolygon
  and 244 MultiLineString features. The legacy `$type` filter, which
  GP-5's description used, folds Multi\* into the base type; docs/adr/008
  swapped it for the expression form and lost that. Latent, not the cause
  of the above.

### Open threads

- **No test in this repo has ever rendered a real map.** Every map test
  mocks `react-map-gl`, because jsdom has no WebGL. 71 green tests
  alongside a completely non-functional renderer. One browser-level test
  asserting `querySourceFeatures(...).length > 0` after a draw would have
  caught this immediately, and would have caught it long before GP-5 — the
  first footprint never rendered either. This needs a ticket and a
  browser-test tool; Playwright was the option discussed.
- **The fix is not verified by anyone but the tooling.** Vite re-optimised
  and both module and worker now serve 200, but the map was not confirmed
  rendering in a browser before this was committed.
- **The coordinate feature has no Jira ticket**, and is the first Map work
  in a while that Gate B does not block.
- **`window.__map` is dev-only and deliberate.** Remove it if it ever
  looks like a leak; it is guarded by `import.meta.env.DEV`.
