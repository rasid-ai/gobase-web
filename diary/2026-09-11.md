# 2026-09-11 — Moving the repo to an org, and the GHCR credential trap

## 11:40 — The owner change: what breaks and what does not

No code changed. This session was diagnosis and a deploy plan.

The repo moved from a personal GitHub account to an organization. The
question was what has to change so the VPS can still pull its images from
GHCR (GitHub's container registry, where the built images live).

### What was found

**Nothing in the repo needs editing.** The owner is never hardcoded. CI
builds the image name from `github.repository_owner` at run time and
lowercases it (`.github/workflows/deploy.yml:59`); the VPS builds it from
`GHCR_OWNER` in its own `.env` (`infra/docker-compose.prod.yml:14`). A grep
for the old owner name across the repo returns nothing. So the whole change
is two host-side values and some org settings.

**GHCR packages do not move with a repo transfer.** Packages belong to the
account, not the repo. The org therefore has no images at all until CI runs
again, and the pre-transfer images stay under the personal account. Order
matters: push first, then deploy, or `deploy.sh` pulls a tag that does not
exist yet.

**Rollback across the transfer is broken.** `deploy.sh` pulls
`ghcr.io/$GHCR_OWNER/...`, so rolling back to any SHA built before the move
fails — those images only exist under the old owner. Recovering one means
setting `GHCR_OWNER` back by hand, or re-pushing the old tags to the org.
This defeats the "a rollback is a single command" promise in
`infra/deploy.sh:6`.

### Decisions

- **Isolate this project's GHCR login with `DOCKER_CONFIG`, rather than
  logging in again as the `deploy` user.** Docker stores one credential per
  registry host, so `docker login ghcr.io` overwrites whatever is in
  `~/.docker/config.json`. The deploy VPS runs other projects that pull from
  the same host, and they would have broken at their next deploy, not
  immediately. Pointing `DOCKER_CONFIG` at `/srv/geo-portal/.docker` gives
  this project its own credential file and leaves the shared one untouched.

  Rejected: a second `docker login` as the `deploy` user (silently breaks
  the neighbours), and a separate Linux user per project (larger change to
  a host that already works).

  It needs no repo change. `infra/deploy.sh:17-19` wraps the `.env` load in
  `set -a` / `set +a`, so every value in `.env` is already exported to the
  `docker compose` calls that follow. One line in the host `.env` is enough.

- **Use one classic PAT on the personal account, scoped `read:packages`.**
  That scope follows what the token's owner can read, so a single token
  covers both the org's new packages and the personal account's old ones —
  which is what a rollback to a pre-transfer SHA needs. An org-scoped or
  machine-account token could not read both.

### Open threads

- **None of it is done yet.** The org settings, the PAT, the `.env` edits
  and the first push are all still to do. Nothing has been run against
  either VPS.
- **Two hosts, not one.** `infra/README.md:7` says the firm's VPS deploys
  from `main` and the developer VPS from `dev`. Each has its own `.env` and
  its own Docker credential file, so both need the same treatment. Deploy
  `dev` first — same pipeline, lower stakes.
- **`DOCKER_CONFIG` only applies through `./deploy.sh`.** Compose reads
  `.env` for substitution into the compose file, not for the Docker CLI's
  own config directory. A hand-typed `docker compose pull` on that host will
  miss it and fail.
- **Org settings are the likely first failure.** Third-party actions must be
  allowed (the workflow uses five), package creation must be permitted, and
  a classic PAT needs SSO authorization if the org enforces SAML. An
  unauthorized PAT returns `denied`, which reads like a wrong scope.
- **`KB_DB_PORT` is wrong in the local `.env`.** It says 5433, but nothing
  listens there and `pg_lsclusters` shows a single cluster on 5432 — which
  is what docs/adr/002 describes. The `kb` role does exist on 5432. Unused
  so far, so it has never failed; the Maps work is the first thing that
  will hit it.
- **`infra/README.md` section 2b does not mention the credential
  collision.** It covers ports, nginx and image pruning for a shared host,
  and stops there. The collision is the one that would actually have caused
  an outage.
